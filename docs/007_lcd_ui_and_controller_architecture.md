# 007 LCD 界面与四端控制架构决议

状态：界面布局、ARM 同步核心、三端协议、参数存储和上电默认关闭策略均已
实现。最终寄存器与帧格式见 `009_three_controller_control_protocol.md`。

## 1. 总体优先级

系统首先必须支持不连接上位机，仅通过屏幕和按键完成日常设置、启动、状态
观察和掉电保存。上位机是可选的测量、监视和维护入口，不能成为设备正常启动
或恢复配置的必要条件。

上位机新 API 仍必须随 FPGA、ARM 和 MCU 协议一起更新，但本阶段不把新增参数
编辑功能接入上位机界面。保留经过版本识别的 API，供后续界面和自动化使用。

## 2. LCD 第一页

屏幕为 160 x 128，左侧 14 像素保留按键图标，右侧内容区按 16 像素行高分为
八行。

| 行 | 内容 | 设置属性 |
|---|---|---|
| 1 | 微波源状态、功率 | 保持原设计 |
| 2 | 微波源频率 | 保持原设计 |
| 3 | 锁相环开关、锁定和通信状态 | 保持原设计 |
| 4 | `中心频率:125000Hz` | 可设置真实频率，限制 `4--125 kHz`；低于 100 kHz 时显示 0.1 Hz 位 |
| 5 | `倍:0040 除:0001` | MUL、DIV 分别显示和设置，不再隐含固定 40 倍 |
| 6 | `频:+0012 相:-0003` | 只显示 ARM 换算后的真实频率、相位残差 |
| 7 | `出:880000Hz` | 只显示 ARM 计算后的锁相环输出频率 |
| 8 | `计:50.000000MHz` | 只显示快速频率计参考值，分辨率 1 Hz |

旧 STM32 公式把真实频率提前乘以 40 后换算为 DDS 相位字。新协议删除这一
隐含关系：STM32 只发送真实中心频率，ARM 负责换算相位增加字。FPGA 内固定
`pre-IQ CIC R=40` 是采样抽取率，与输出 MUL/DIV 无关。

第 4 行沿用原小数点处理方式，以 `0.1 Hz` 为编辑和传输分辨率。第 8 行接收
ARM 已换算好的整数 Hz，再在倒数第六位前插入小数点，例如：

```text
50000001 Hz -> 50.000001 MHz
```

## 3. LCD 第二页

第二页不再显示微波源区域，八行全部用于锁相参数设置：

| 行 | 界面名称 | 参数 |
|---|---|---|
| 1 | `追踪P` | `Kp_track` |
| 2 | `追踪I` | `Ki_track` |
| 3 | `捕获f` | `Kf_acquire` |
| 4 | `过渡f` | `Kf_blend` |
| 5 | `上限` | 输出正限幅 |
| 6 | `下限` | 输出负限幅 |
| 7 | `相残` | 相位残差阈值 |
| 8 | `幅度x.xxV 频残xxx` | 幅度和频率残差阈值两个独立设置项 |

`Kf_blend` 采用“过渡f”，因为 BLEND 是从捕获向稳定追踪过渡的环路状态；
“混频”容易与信号混频器混淆，“融合f”也不如“过渡f”直接。

最后一行不显示相位残差阈值。其固定样式为：

```text
幅度2.00V 频残999
```

该字符串按现有 16 x 16 汉字和 8 x 16 ASCII 字宽约占 136 像素，可放入 146
像素内容区，无需改用小字体。幅度和频残分别响应光标和闪烁编辑。

## 4. 参数所有权和数据单位

LCD/按键模组是日常参数管理入口。STM32 只保存、编辑和显示物理量，不再执行
DDS、NCO、FPGA 定点格式或 80 bit 频率计换算。

建议的新协议物理量如下：

| 参数 | STM32/协议单位 | ARM 职责 |
|---|---|---|
| 中心频率 | 无符号整数，`0.1 Hz/LSB` | 换算 DDS 中心字并选择频点 profile |
| MUL/DIV | 无符号整数 | 检查非零、位宽和输出溢出 |
| 输出上下限 | 有符号整数 Hz | 换算为 signed DDS 修正字 |
| 相位残差阈值 | 待确认的物理相位单位 | 换算 FPGA phase threshold |
| 频率残差阈值 | 整数 Hz | 换算 FPGA frequency threshold |
| 幅度 | mV，界面按 V 显示 | 换算 DAC amplitude word |
| 四个环路增益 | 无符号整数 | 合法性检查并写入对应 shadow 寄存器 |
| 实时频率残差 | ARM 输出物理值 | STM32 只负责符号和十进制显示 |
| 实时相位残差 | ARM 输出物理值 | STM32 只负责符号和十进制显示 |
| DPLL 输出频率 | ARM 输出整数 Hz | STM32 直接显示为 Hz |
| 快速频率计 | ARM 输出整数 Hz | STM32 插入六位小数并显示为 MHz |

## 5. 四端职责

### 5.1 FPGA

- 执行实时 DPLL、状态机、DDS、MUL/DIV 和 DAC 数据通路。
- 保留原触发式精密频率计作为正式测量通道。
- 提供自动更新的快速参考频率通道用于 LCD 和上位机监视。
- 只接收明确的定点寄存器值，不理解 LCD、EEPROM 或 PC 界面语义。

### 5.2 Zynq ARM

- 是物理量与 FPGA 定点寄存器之间唯一的换算层。
- 接收 STM8 转发的屏幕设置，验证完整参数后一次性 APPLY。
- 根据真实中心频率生成 CIC、IIR、dwell、timeout 和未在 LCD 暴露的 profile
  参数。
- 把 FPGA 原始状态、残差、输出字和快速计数结果换算成 STM32 可直接显示的
  物理量。
- 同时维护屏幕协议和上位机 API，并提供设备版本、能力和协议版本识别。

### 5.3 STM8

- 作为 STM32 I2C 与 ARM UART 之间的轻量通用转发器。
- 管理 EEPROM 和微波源/MAX2871。
- 不解释 DPLL 参数含义，不执行频率、相位或定点换算。
- 新协议应允许转发未知寄存器号和可变长度数据，使少量增删寄存器不要求重烧
  STM8。

### 5.4 STM32F030

- 管理 LCD、按键、页面、光标、数值编辑和用户可见状态。
- 以物理量读写参数，并触发保存；不再生成 FPGA 相位字。
- 上电时能够从 STM8/ARM 读取完整当前配置并恢复显示。
- 在没有上位机的情况下完成全部日常操作。

### 5.5 上位机

- 新程序必须识别并兼容旧设备协议和新设备协议。
- 新 ARM 不要求兼容旧上位机。
- 新 API 必须覆盖屏幕可设置参数、快速参考频率和原精密测量流程。
- 本阶段新增 API 不接入界面；上位机正常运行只负责测量、状态和数据读取。
- 将来启用参数写界面时，必须通过 ARM 的同一套物理量校验和 APPLY 流程，不能
  绕过屏幕配置模型直接写 FPGA 原始寄存器。

## 6. 当前待继续讨论

1. 相位残差实时值和相位阈值采用度、0.1 度还是其他物理单位。
2. STM8 通用寄存器转发帧、最大单帧长度、读写和错误码格式。
3. EEPROM 采用固定物理参数区还是轻量寄存器记录表，以及掉电保存触发策略。
4. ARM、STM8、STM32 和 PC 同时写参数时的所有权、同步与持久化规则。

## 7. 老代码的实际上电时序

老系统不是 STM8 或 ARM 自动恢复配置，而是由 STM32 屏幕程序主动发起。

### 7.1 ARM 先建立临时默认配置

ARM 启动后依次完成：

1. 初始化 PC UART0 和 STM8 UART1。
2. 复位 FPGA 并检查 DPLL ABI。
3. 关闭 DPLL 输出。
4. 写入编译在 ARM 程序中的 22 kHz profile、MUL=1、DIV=1 等默认值。
5. APPLY 这套临时默认配置。
6. 进入循环等待 STM8 或 PC 命令。

因此 ARM 可以先形成一套 active 配置，但它没有主动读取 STM8 EEPROM。DPLL
保持关闭，等待后续控制。

### 7.2 STM8 启动后不主动读取 EEPROM

STM8 初始化 I2C、UART、MAX2871 和定时器后直接进入命令循环。其 `main` 中
自动调用 `EEPROM_Read_Data()` 的代码已经注释。只有收到 STM32 的 I2C `C2`
命令后，STM8 才把 EEPROM 数据加载到 `IIC_Reg_Buff`。

### 7.3 STM32 是真正的启动发起者

STM32 显示约两秒启动画面后执行 `STM8Slave_Init()`：

1. 等待 STM8 I2C 地址和 `0xA5` 标识可读。
2. 发送 `C2`，命令 STM8 从 EEPROM 加载配置。
3. 从 STM8 读取完整 52 字节寄存器区到 STM32 本地缓存。
4. 发送 `C9`，经 STM8 UART 命令 ARM/FPGA 复位。
5. 发送 `C4`，由 STM8 把 EEPROM 中偏移 8 开始的 34 字节 PLL 配置转发给
   ARM。
6. ARM 将这 34 字节解释为中心字、MUL/DIV、四个增益、限幅、阈值和幅度，
   写 FPGA 并 APPLY。
7. STM32 根据刚才读取的本地副本初始化显示值。

所以老代码的准确结论是：

- 启动命令发起者：STM32。
- 掉电参数来源：STM8 EEPROM。
- 参数转发者：STM8。
- 参数验证和 FPGA 生效执行者：ARM。
- ARM 编译默认值：只是在收到 STM8 配置前使用的临时值。

## 8. “缓存覆盖”的具体含义

当前系统同时存在至少三份配置：

1. STM32 RAM 中用于编辑和显示的 `STM8_Slave_Data`。
2. STM8 RAM/EEPROM 中的 `IIC_Reg_Buff` 和掉电副本。
3. ARM/FPGA 已通过校验并实际生效的 active 配置。

“覆盖”指这些副本不一致时，一端发送整块配置或重新启动，会把另一端较新的值
替换掉。老代码存在以下具体情况。

### 8.1 PC 写入会被下一次屏幕操作覆盖

PC 旧接口直接修改 ARM/FPGA，但对应 STM8 EEPROM 更新代码已注释。此时 ARM
active 是新值，而 STM8 EEPROM 和 STM32 缓存仍是旧值。下一次屏幕只修改一个
参数时会重新发送整块 34 字节旧缓存，从而把 PC 修改的其他参数一起覆盖。

### 8.2 重启会用 EEPROM 覆盖 ARM 临时配置

ARM 每次启动先应用编译默认 profile。STM32 随后发送 C4，又以 EEPROM 配置
覆盖 ARM 默认值。这是老代码的正常设计，但没有版本和来源记录。

### 8.3 ARM 拒绝后，屏幕和 EEPROM仍可能保存未生效值

STM32先修改本地缓存和 STM8寄存器，再要求 ARM APPLY，并在约十秒后触发
EEPROM 保存。屏幕函数没有读取 ARM 的 applied snapshot 来回滚。如果 ARM 因
范围、ABI 或 APPLY 错误拒绝配置，可能出现：屏幕显示新值、EEPROM保存新值，
但 FPGA 实际仍运行旧值。

### 8.4 ARM 单独复位后不会自动恢复 EEPROM 配置

如果 ARM 重启而 STM32 没有同时重启，ARM只加载编译默认值；STM32周期刷新只
读取状态，不会自动重发完整 EEPROM 配置。设备可能一直保持默认且关闭，直到
用户修改参数或重启屏幕。

### 8.5 STM32 单独复位会复位整个 DPLL

STM32每次初始化都会发送 C9，导致正在工作的 ARM/FPGA DPLL 被复位，然后再
发送 EEPROM 配置。一个纯显示控制器复位会中断实时环路。

## 9. 推荐的新上电和同步规则

推荐把“主动恢复配置”的责任从 STM32 移到 ARM。屏幕仍是最高优先级的日常
用户入口，但 ARM 最清楚 FPGA ABI、APPLY 时机和配置是否合法。

### 9.1 建议的权威层次

- STM8 EEPROM：持久化的期望配置。
- ARM applied snapshot：硬件当前实际生效配置，运行时唯一真值。
- STM32 RAM：ARM applied snapshot 的显示/编辑副本，不是独立权威配置。
- PC API：另一个可选的参数请求入口，不直接拥有一份独立配置。

PLL使能和输出使能不属于持久化配置，不写入EEPROM。任何整机上电、ARM复位
或FPGA复位后都默认关闭。ARM恢复并验证参数后也不得自动重新使能，必须等待
屏幕或将来上位机发出新的显式开启命令。

### 9.2 建议上电流程

1. STM8上电后自动加载EEPROM到简单的通用寄存器区。
2. STM32通常先于ARM完成启动。STM32照常初始化页面并轮询ARM；通信不通就直接
   使用现有通信故障状态，不增加“ARM启动中”等新界面状态。
3. PLL使能和输出使能上电默认关闭且不保存。ARM未启动时自然不能开启。
4. STM32不得再在初始化时发送C9，也不得把整块本地缓存盲目推给ARM。
5. ARM完成UART、FPGA复位和ABI检查后，主动从STM8读取持久化参数，校验、生成
   profile并一次性APPLY；PLL和输出仍保持关闭。
6. STM32下一次状态轮询成功后，再读取一次ARM实际配置刷新页面，并清除通信
   故障。以后实时数据和配置readback都以ARM为准。
7. ARM单独复位会自行重新加载STM8配置；STM32单独复位只重建页面，不中断
   DPLL。

这套流程不需要STM32维护待应用/已应用两套缓存，也不需要新增启动阶段状态机。
通信失败就是通信失败；通信恢复后重新读取ARM实际值即可。

### 9.3 建议运行时写入流程

1. STM32编辑一个物理参数并向 ARM提交“期望修改”。
2. ARM基于当前 active snapshot 合并该字段，补齐派生参数并校验完整配置。
3. APPLY成功后，ARM返回成功状态和规范化物理值。
4. STM32收到成功响应后才更新正式显示缓存；失败则保留原值并显示错误状态。
5. ARM或STM32通知STM8更新持久化寄存器；STM8继续采用延时合并写EEPROM，
   避免按键每变化一次就写Flash。

这样不再由STM32发送整块陈旧结构，也不会因为改一个字段覆盖其他入口刚修改
的字段。

### 9.4 未来 PC API 写入规则

PC必须走与屏幕相同的ARM合并、校验、APPLY和readback流程。API应明确区分：

- 临时应用：改变active配置但不写EEPROM，用于调试。
- 应用并保存：成功APPLY后同步STM8并触发EEPROM保存。

无论哪种写入，STM32在后续状态/配置刷新时都应读取ARM实际值，不能继续显示
旧缓存。当前PC界面不接参数设置，但API语义应提前按此定义。
